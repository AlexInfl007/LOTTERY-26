# Глубокий аудит проекта LOTTERY-26

Дата: 2026-03-06

## 1) Краткий вердикт

Проект уже имеет крепкий фундамент для Web3 dApp (React + Vite, мультиязычность, явная работа с Polygon, централизованный контрактный слой), но в текущем виде есть несколько архитектурных и продуктовых проблем, которые снижают надежность и UX в реальном использовании.

**Общий уровень готовности:** средний (MVP-подобный), с высоким потенциалом после исправления критических пунктов ниже.

---

## 2) Сильные стороны

1. **Хорошая модульность фронтенда**
   - Логика разнесена по компонентам и util-слоям (`WalletConnect`, `ethersUtils`, `contractManager`). Это упростит дальнейший рефакторинг.

2. **Есть проверка сети и явный переход на Polygon**
   - В `walletConnector` корректно предусмотрен `wallet_switchEthereumChain` и добавление сети при `4902`.

3. **Предусмотрена устойчивость к ошибкам RPC**
   - В коде есть retry/backoff паттерны и перехват типовых RPC-ошибок.

4. **Международная локализация уже встроена**
   - Подключены 8 локалей, базовая i18n-инфраструктура готова к масштабированию.

5. **Собирается production-бандл без падений**
   - `npm run build` проходит успешно.

---

## 3) Слабые стороны

1. **Избыточно сложный слой инициализации контракта**
   - Одновременно используются `ethersUtils` и `contractManager`, что усложняет поток данных и увеличивает вероятность гонок/циклических зависимостей.

2. **Продуктовые ожидания UI не совпадают с реальной on-chain моделью**
   - В интерфейсе есть «Live feed» и «Recent winners», но в коде часть этого фактически не реализована полностью (см. ошибки ниже).

3. **Недостаточная строгость CSP**
   - CSP включает `unsafe-inline` и `unsafe-eval`, что ухудшает защиту от XSS.

4. **Неполная локализация**
   - Во многих языках отсутствует часть ключей (fallback на дефолт/английский).

5. **Большой клиентский бандл**
   - Главный JS chunk >500KB после минификации; это ухудшает TTI на мобильных устройствах.

---

## 4) Подтвержденные ошибки и риски (приоритет)

## P0 / Критично

### 4.1. Циклическая зависимость между `ethersUtils` и `contractManager`
- `ethersUtils` импортирует функции из `contractManager`.
- `contractManager` импортирует `getCurrentProvider` из `ethersUtils`.
- Это классический circular dependency риск: трудно предсказать порядок инициализации, особенно в edge-сценариях и при hot reload.

## P1 / Высокий

### 4.2. Утечка подписок/обработчиков в `App.jsx`
- Внутри `useEffect` создается async-функция `initializeData`, которая **возвращает cleanup**, но этот cleanup не используется React, потому что возвращается из async-функции, а не из самого `useEffect`.
- Итог: потенциально не снимаются подписки (`unsubscribeTicket`, `unsubscribeWinner`, `poolUnsubscribe`) при размонтировании.

### 4.3. `watchTicketEvents` заявлен, но фактически не работает
- Функция создает handler, но затем явно возвращает пустой unsubscriber, т.к. "нет события" в ABI.
- При этом UI показывает live-feed событий покупки билетов, что вводит в заблуждение относительно реальных ончейн-событий.

### 4.4. `watchPrizePoolUpdates` не реализован (пустышка)
- Функция возвращает пустой unsubscriber и не подписывает ни на какие события.
- В `App.jsx` создается видимость event-driven обновления пула, но фактически работает только polling.

### 4.5. `getRecentWinners` всегда возвращает пустой массив
- В реализации явно указано, что исторические победители не извлекаются из цепочки и возвращается `[]`.
- Компонент Winners становится декоративным без фактических данных.

## P2 / Средний

### 4.6. Дублирование ABI и адреса контракта в двух местах
- ABI/адрес находятся и в `src/utils/contract.js`, и в `utils/contractManager.js`.
- Это риск рассинхронизации при обновлениях контракта.

### 4.7. Потенциально несовместимый fallback через `provider.sendAsync`
- Используется fallback `sendAsync`, который отсутствует у части современных EIP-1193 провайдеров.
- Это может приводить к runtime ошибкам на некоторых кошельках.

### 4.8. Слабая CSP-политика для production
- В CSP присутствуют `'unsafe-inline'` и `'unsafe-eval'` + очень широкие allowlists.
- Это снижает уровень hardening для web-приложения с финансовым контекстом.

### 4.9. Неполные переводы
- Проверка ключей показала значительное количество пропусков во всех локалях кроме `en`.

### 4.10. Перегруженный бандл
- Сборка сигнализирует о chunk > 500KB (code-splitting требуется).

## 7) Дополнительное исследование (2026-04-09)

Ниже — ошибки/некорректная логика, выявленные при повторном просмотре актуального кода после доработок Live Feed.

### P1 / Высокий

#### 7.1. Рассинхронизация состояния после `accountsChanged`
- В `WalletConnect` обработчик `onAccountsChanged` обновляет только локальные `connected/address`, но **не вызывает `onConnect(...)`**, не обновляет shared provider и signer для `App`.
- Риск: верхний уровень приложения продолжает работать со старым `walletAddress`/`signer`, а UI кнопки уже показывает новый аккаунт.

#### 7.2. Ветка `getCurrentWalletAddress()` не синхронизирует App-состояние
- В `checkExistingConnection` при успешном `getCurrentWalletAddress()` выставляется только локальный `connected/address`.
- `onConnect(...)` в этой ветке не вызывается, поэтому контрактный слой на уровне `App` может остаться неинициализированным для этого пользователя.

### P2 / Средний

#### 7.3. Live Feed не перезасевается, если начальный скан не нашел историю и счетчик не меняется
- Фид перезапрашивается только если `updatedTicketsCount > previousCount`.
- Если при первом входе скан не нашел транзакции (RPC ограничение/окно блоков), а новых покупок нет, блок остается пустым неопределенно долго, хотя в контракте могли быть исторические покупки.

#### 7.4. Очень тяжелый клиентский скан блоков для истории покупок
- `getRecentTicketPurchases` итерирует блоки по одному (`for` от latest до fromBlock).
- Адаптивное окно до `400000` блоков может вызвать длительные запросы RPC, лаги и таймауты на части кошельков/провайдеров.

#### 7.5. Комментарий в инициализации не соответствует факту ожидания
- В `App` указан комментарий про «max 10 seconds with retries», но фактическая задержка между ретраями реализована через `MessageChannel` и происходит практически мгновенно.
- Это создает ложное ожидание по таймингам и осложняет отладку сетевых проблем.

### Что рекомендую сделать следующим шагом

1. В `WalletConnect` при `accountsChanged` и при ветке `getCurrentWalletAddress()` вызывать `onConnect(...)` с актуальными `provider/signer`.
2. Для Live Feed добавить периодический «мягкий reseed» даже без роста `ticketsCount` (реже, например раз в 3–5 минут).
3. Заменить блочный полный скан на более дешёвую стратегию:
   - ограниченные батчи + early stop + кэш последнего найденного блока/tx,
   - либо индексаторный источник (если приемлемо по архитектуре).
4. Исправить retry-delay в инициализации на реальный `setTimeout`-based backoff и выровнять комментарии с реальным поведением.
